ワークノート管理（管理者用アプリ）仕様書

作成日 2026-10-26アプリ名 ワークノート管理対象 Web（iPad・Mac・PC）バックエンド Firebase（従業員アプリと共用）

01概要

管理者が日報・経費・打刻の修正申請を承認し、全員の勤怠を確認・修正し、勤務先や会社の設定などのマスタを管理し、見積書を作成するためのアプリです。従業員用 iPhone アプリ「ワークノート」と同じ Firebase のデータを使います。

ブラウザで動く Web アプリとして作ります。iPad・Mac 用には、この Web アプリを画面いっぱいに表示する専用アプリ（WebView）も用意します。どちらで使っても中身は同じです。

今回の対象

  • Web アプリ（iPad・Mac・Windows のブラウザ）
  • iPad・Mac 用の専用アプリ（WebView で表示）
  • 承認（日報・経費・打刻の修正申請）
  • 全員の勤怠の確認、打刻の直接修正・追加・削除
  • マスタの管理（従業員・勤務先・休業日・日報の項目・経費の区分・会社の設定）
  • 見積書の作成と PDF の出力・共有

今回の対象外（後で検討）

  • ログイン用アカウントの完全な削除・無効化（Firebase コンソールで行う。未決事項）
  • 勤怠・経費の CSV 出力（給与・会計ソフトへの連携）
  • 見積書の印影、請求書への変換
  • 通知（承認待ちが増えたときのメールなど）
前提　従業員アプリのデータの形（Models.swift）と計算（WorkNoteCore）に合わせます。従業員アプリのコードは変更しません。必要な変更は 12. 従業員アプリへの提案 にまとめます。

02システム構成

Web アプリを Firebase Hosting に置き、ブラウザまたは専用アプリから開きます。データは従業員アプリと同じ Cloud Firestore を読み書きします。料金プランは Spark（無料）のままで動くようにします。

03ログインと権限

  • 従業員アプリと同じメールアドレスとパスワードでログインします。一度ログインすれば、次からは自動でログイン状態になります。
  • ログイン後に users/{uid}.role を確認し、admin でなければ「管理者のアカウントではありません」と表示します。この画面ではログアウトだけができます。
  • パスワードを忘れたときは、ログイン画面から再設定メールを送れます。
  • 管理者のアカウントは、管理者アプリの「従業員」画面で権限を「管理者」にして作ります。最初の1人は、従業員アプリのスクリプト（npm run create-user -- <email> '<password>' '<名前>' admin）で発行します。
権限管理者アプリできること
従業員employee使えない—（従業員アプリだけ）
管理者admin使える全員分の閲覧、承認・差し戻し、打刻の修正、マスタの変更、見積書の作成

できる操作は画面だけでなく、Firestore のセキュリティルールでも制限します（10. セキュリティルール）。

05承認

日報

下書き→ 提出 →提出済み→ 承認 →承認済み
提出済み／承認済み→ 差し戻し（理由） →下書き
  • 確認：日報の項目（settings/reportTemplate の並び順）、勤務先、写真、提出日時、更新日時を表示します。
  • 修正履歴：revisions を新しい順に並べ、変わった項目は修正前を取り消し線で表示します（従業員アプリと同じ表示）。
  • 承認：status を approved にし、approvedBy と approvedAt を記録します。承認すると、本人は修正できなくなります。
  • 差し戻し：理由を必ず入力します。status を draft に戻し、returnReason・returnedBy・returnedAt を記録します。承認済みの日報も差し戻せます。 従業員アプリの日報の状態には「差し戻し」がないので、新しい状態の値は作らず「下書き」に戻します。
  • 一覧の初期表示は「提出済み」です。状態ごとの件数も表示します。
  • まとめて承認：一覧で複数の日報を選び、一度に承認できます。

経費

申請済み→ 承認 →承認済み
申請済み／承認済み→ 差し戻し（理由） →差し戻し→ 本人が直して申請 →申請済み
  • 確認：利用日・金額・お店・会社名・区分・インボイス番号・メモ・申請日時と、領収書の画像・OCR テキスト（読み取った全文）を表示します。
  • 承認：status を approved にし、reviewedBy と reviewedAt を記録します。
  • 差し戻し：理由を必ず入力します。status を returned にし、returnReason・reviewedBy・reviewedAt を記録します。従業員アプリには差し戻しの理由が表示されます。
  • 合計：月を選び、申請済み・承認済みの経費の合計を、従業員ごと・区分ごとに表示します。下書きと差し戻しは合計に入れません。
  • インボイス番号が空の経費には「インボイス番号なし」の印を付けます。
  • まとめて承認：一覧で複数の経費を選び、一度に承認できます。

打刻の修正申請

申請中→ 承認 →承認済み（勤怠に反映）
申請中→ 却下（理由） →却下
  • 確認：申請の種類・勤務日・正しい時刻・休憩・理由を表示します。その日の今の打刻と、承認したあとの打刻と集計（実働など）を並べて比べられます。
  • 承認：下の表のように打刻を書き換え、申請の status を approved にし、reviewedBy と reviewedAt を記録します。申請と打刻は1回でまとめて書き込みます（トランザクション）。書き込む直前に、申請がまだ「申請中」か確かめます。本人が取り消した申請は承認しません。
  • 却下：理由を必ず入力します。status を rejected にし、rejectReason・reviewedBy・reviewedAt を記録します。
  • 修正申請の期限（締め日の翌月の第3営業日）は、本人が申請するときだけの制限です。期限を過ぎていても、管理者は承認・却下できます。
申請の種類承認したときの反映
出勤の打刻漏れmissingClockInrequestedClockIn・requestedClockOut のうち入っているものを、それぞれ次のように反映する。
  • targetPunchIds の中に同じ種類（出勤／退勤）の打刻があれば、その punchedAt を書き換える。
  • なければ、打刻を新しく追加する（勤務日は申請の workDate、位置は「位置なし」）。
どちらの場合も、打刻に corrected: true と correctionId を付ける。書き換えたときは元の時刻を originalPunchedAt に残す（すでに入っていれば上書きしない）。
退勤の打刻漏れmissingClockOut
時刻の誤りwrongTime
休憩を取れなかったnoBreak打刻は変えない。申請を承認するだけで、従業員アプリがその日の休憩に requestedBreakMinutes を使う。管理者アプリの集計も同じ。

休暇（leaveRequests）

  • 従業員アプリから1日1件で申請されます（まとめて申請した日は groupId が同じ）。データの形は docs/従業員アプリ指示書_休暇.md。
  • 種類は有給（全日・午前半休・午後半休）・特別休暇・欠勤。有給は理由なしでも申請できます。
  • 一覧は「申請中・承認・却下・取り消し・すべて」と月・従業員で絞り込み、まとめて申請した日は1行にまとめます。申請中はまとめて承認できます。却下は理由が必須です。
  • 「休暇を登録」で、管理者が承認済みの休暇を直接登録できます（電話で連絡を受けたときなど）。勤怠の日ごとの詳細からも登録できます。
  • 承認済みの休暇は本人からは取り消せません。管理者が理由を付けて「取り消し」にします（記録は残す）。
  • 勤怠の月の集計に、有給・特別休暇・欠勤の日数（承認済みのみ、半休は0.5日）と申請中の件数を出します。全日の休暇の日は日報の未提出に数えません。

06勤怠の確認・修正

出勤状況

  • 在籍している全員の今日の状態（勤務中・前日から勤務中・打刻漏れ・退勤・未出勤・休暇・休み）、出勤・退勤の時刻、経過・実働、最後に打刻したときの場所（地図へのリンク）、日報の提出を一覧にします。打刻があると自動で更新されます。
  • 場所は打刻したときの位置で、今いる場所ではありません。中抜け中の人は「退勤」になります。
  • ホームにも状態ごとの人数を出します。

全員の月の集計

月（締め日で区切る）を選ぶと、従業員ごとに次の値を表示します。

表示例です。日報未提出は、打刻がある日に提出済み・承認済みの日報がない日の数です。

  • 勤務ごとの出勤・退勤の時刻、住所、位置の精度、「打刻から◯分後に取得」、サーバーが受け取った時刻を表示します。

  • 修正済みの打刻には、元の時刻・どの修正申請か・修正した管理者を表示します。
  • 集計（拘束・中抜け・休憩・実働・時間外）と、その日の日報・修正申請へのリンクを表示します。

管理者による打刻の直接修正

修正申請の期限を過ぎた月や、申請がなくても直す必要があるときに使います。どの操作でも、理由の入力を必須にします。

操作内容
時刻の修正punchedAt を書き換え、corrected: true・originalPunchedAt（最初の時刻）・correctedBy・correctedAt・correctionReason を記録する。出勤・退勤の種類と勤務日は変えない。
打刻の追加勤務日・種類（出勤／退勤）・時刻を指定して追加する。corrected: true、位置は「位置なし」、correctedBy・correctedAt・correctionReason を記録する。
打刻の削除二重押しなどの間違った打刻を消す。消す前の内容をすべて punchDeletions/{id} に記録として残す（誰が・いつ・理由も残す）。この記録は変更・削除できない。
休憩の修正この日の休憩を指定した分にする。管理者が「休憩を取れなかった」の修正申請を代わりに作り、承認済みの状態で登録する（createdBy に管理者を記録）。
注意　勤務日をまたいで打刻を移したいとき（勤務日の付け間違いなど）は、削除と追加で直します。保存する前に、直したあとの集計を確認画面で表示します。

07マスタの管理

従業員（users）

  • 一覧：名前・メールアドレス・権限・登録日を表示します。名前で検索できます。
  • 追加：メールアドレス・初期パスワード（8文字以上）・名前・権限を入力します。
    • アカウントは、管理者のログインとは別の2つ目の Firebase の接続で作り、作ったらすぐにその接続からログアウトします。
    • users/{uid} は管理者の接続で書きます。
    • アカウントだけできて users/{uid} の書き込みに失敗したときは、もう一度書き込む画面を出します。
  • 変更：名前と権限（従業員／管理者）を変えられます。自分の権限は変えられません（管理者がいなくなるのを防ぐため）。メールアドレスは変えられません。
  • パスワード：再設定メールを送れます。管理者がパスワードを直接見たり変えたりすることはできません。
  • 退職：詳細画面の「退職にする」で、退職日（記録用）とメモを入れて users/{uid} に retiredAt・retiredBy・retireDate・retireReason を書きます。保存した時点から、その人はルールで自分の users/{uid} を読むこと以外できなくなります（打刻・日報・経費・設定も読めない）。退職した管理者は管理者の操作もできません。自分は退職にできません。「退職を取り消す」で元に戻せます。
  • 退職した人は一覧・選択欄では後ろに「（退職）」を付けるか、隠します（「退職した人も表示」で出せる）。過去の勤怠・日報・経費は消さず、名前も出します（勤怠の記録は法律で保存が必要なため）。
  • ログイン用のアカウントは残ります。完全に消すときは Firebase コンソールの Authentication で削除します（画面にリンクを出す）。
  • 追加で「このメールアドレスはすでに使われています」となったとき：登録済みの人ならその人を開くボタンを、ログイン用のアカウントだけが残っている場合は Firebase コンソールで消して追加し直す手順を表示します。

勤務先（sites）

  • 名前・住所・使う／使わない（active）・並び順（order）を変えられます。
  • 日報が勤務先を ID で参照しているので、削除はしません。使わない勤務先は「使わない」にすると、従業員アプリの選択肢に出なくなります。
  • 名前・住所で検索できます。上下に動かして並び順を変えられます。

休業日（settings/calendar_{yyyy}）

  • 年を選び、日付・名前・種類（国民の祝日／会社の休業日）を追加・削除します。
  • 修正申請の期限の計算と、勤怠の休日の色分けに使われます。
  • 年をまたぐ休業日（年末年始など）は、それぞれの年に登録します。

日報の項目（settings/reportTemplate）

  • 項目の追加、名前・必須・並び順の変更ができます。
  • 追加した項目のキーは自動で決め、あとから変えられません。種類は「1行テキスト」「長文テキスト」「写真」から選びます。
  • 従業員アプリが特別に扱う項目（日付 date・作業時間 workTime・訪問先・現場名 site・作業内容 content）は、削除や種類の変更ができません。
  • 項目を削除しても、すでに保存された日報の内容は残ります。管理者アプリでは「（削除した項目）」として表示します。

経費の区分（settings/expenseCategories）

  • 区分の追加、名前・判定キーワード・並び順の変更ができます。
  • 「その他」（other）は削除できません。キーワードに当たらない経費はここに入ります。
  • 使われている区分は削除できません。使っている経費の件数を表示します。

08見積書

工事・作業の見積書を作り、PDF で保存・共有します。仕様が決まっていなかった部分は、一般的な形で決めました。

項目入力必須備考
見積番号自動自動「2026-0001」の形（発行年＋年ごとの連番）。保存したときに決まる
件名テキスト必須例：外壁補修工事
宛先テキスト＋敬称（御中／様）必須会社なら「御中」、個人なら「様」
現場勤務先の一覧から選ぶか手入力—現場名・住所を PDF に出す
発行日日付必須初期値は今日
有効期限日付必須初期値は発行日の30日後
明細品名・数量・単位・単価（行を追加・削除・並べ替え）1行以上数量は小数第2位まで。金額＝数量×単価（1円未満切り捨て）
消費税税率（初期値 10%）自動小計×税率、1円未満切り捨て
合計—自動小計＋消費税
備考長文テキスト—支払条件・工期など
担当者テキスト—初期値は作成した管理者の名前
  • 状態：下書き／発行済み。発行済みにしても編集はできますが、更新日時を記録します。
  • 複製：既存の見積書をもとに新しい見積書を作れます（番号は新しく採番）。
  • PDF：A4 縦。印刷用の画面を作り、ブラウザの印刷から「PDF として保存」・共有します。専用アプリでは、端末の PDF 作成と共有シート（保存・AirDrop・メールなど）を使います。 配置：上に「御見積書」と番号・発行日、左に宛先と件名・現場・有効期限、右に発行元、中央に「御見積金額 ¥xxx（税込）」を大きく出し、その下に明細表・小計・消費税・合計・備考を並べる。
  • 見積書は管理者だけが読み書きできます。削除は下書きのときだけできます。

09データ設計

従業員アプリのデータの形はそのままにします。管理者アプリが書き込むフィールドと、新しく作るコレクションは次のとおりです。従業員アプリは知らないフィールドを読み飛ばすので、これらのフィールドを足しても従業員アプリは動きます。

既存のコレクションに足すフィールド

コレクション管理者が書くフィールド
users/{uid}作成時：displayName, email, role, createdAt。変更時：displayName, role
attendancePunches/{id}修正時：punchedAt, corrected, originalPunchedAt, correctionId（申請からの修正）, correctedBy, correctedAt, correctionReason（新しいフィールド）。追加時：従業員の打刻と同じ形で corrected: true、locationStatus: "unavailable"
attendanceCorrections/{id}承認・却下：status, reviewedBy, reviewedAt, rejectReason（新しいフィールド）。管理者が代わりに作る「休憩を取れなかった」：createdBy（新しいフィールド）
dailyReports/{id}status, approvedBy, approvedAt, returnReason, returnedBy, returnedAt（新しいフィールド）
expenses/{id}status, returnReason, reviewedBy, reviewedAt（新しいフィールド）

新しいコレクション

コレクション中身主なフィールド

10セキュリティルール

Firestore のルールはプロジェクトに1つだけです。今反映されている従業員用のルール（WorkNote/firebase/firestore.rules）はそのまま残し、管理者の書き込みを許可する条件を足した1つのファイルにします。従業員側の制限は緩めません。今後は WorkNoteAdmin/firebase/firestore.rules を正本にします。

コレクション管理者に足す許可
userscreate：role が employee か admin、決まったフィールドだけ。update：displayName と role だけ、自分の role は変えられない
attendancePunchescreate：corrected == true、kind・時刻・勤務日の形が正しいこと。update：時刻と修正の記録のフィールドだけ（userId・workDate・kind・位置は変えられない）。delete：同じ1回の書き込みの中で punchDeletions に記録を作るときだけ
attendanceCorrectionsupdate：申請中から承認／却下への変更、reviewedBy が自分。create：承認済みの「休憩を取れなかった」だけ（createdBy・reviewedBy が自分）
dailyReportsupdate：提出済みから承認、提出済み・承認済みから下書き（差し戻し）。状態と承認・差し戻しの記録のフィールドだけ
expensesupdate：申請済みから承認、申請済み・承認済みから差し戻し。状態と承認・差し戻しの記録のフィールドだけ
punchDeletionscreate と read だけ（変更・削除はできない）
estimatesread・create・update。delete は下書きだけ

反映する前に、従業員用ルールとの差分を確認します。反映は firebase deploy --only firestore:rules で行います。Storage のルールは変えません。今のルールでも、管理者は画像を読めます。

12従業員アプリへの提案

今回は従業員アプリを変更しません。次の点は、従業員アプリを直すと使いやすくなります。

  • 日報の差し戻しの理由を表示する：今は下書きに戻るだけで、returnReason が表示されません。
  • 修正申請の却下の理由を表示する：rejectReason を申請のカードに出します。
  • 差し戻し後の修正も修正履歴に残す：今は「提出済み」を直したときだけ履歴を残すので、下書きに戻してから直した内容は履歴に残りません。
  • セキュリティルールのファイルを合わせる：WorkNote/firebase/firestore.rules を管理者アプリの正本と同じ内容にします（従業員リポジトリから古いルールを反映してしまうのを防ぐため）。
